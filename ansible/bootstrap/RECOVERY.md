# Deployment and recovery sequence

Vault is the source of truth for secrets. Terraform state remains in Cloudflare R2.
The ignored root `.env` and GitHub Actions secrets are deployment copies, including
the credentials needed to provision and configure Vault itself.

All commands below run from the repository root and use repository-relative paths.

## Recovery prerequisites

For bootstrap recovery, start with Proxmox administrative access, Cloudflare/R2
access and a protected copy of the root `.env`. This is sufficient to rebuild the
runner, k3s and a fresh Vault and repopulate the operator/CI credentials it contains.
A Vault backup is optional for this bootstrap path.

The commented [.env.example](../../.env.example) in the repository root distinguishes
initial inputs from later service and optional inputs. The private `.env` uses the
same comments with your real values. Keep a protected copy outside the machine being
rebuilt; the Git clone intentionally does not contain it.

| Item | Source of truth / recovery source |
|------|-----------------------------------|
| Terraform resource IDs and state | Existing R2 bucket; preserve every `homelab/...tfstate` object |
| Operator and CI credentials | Protected `.env` for bootstrap; Vault `secret/homelab-infra-secrets` during normal operation |
| Application credentials | Existing per-service Vault records such as `secret/workspaced-secrets` |
| Existing Vault-only secrets and history | Vault LXC/data backup, or an explicit export of those secrets |
| Existing Vault unseal/root material | Needed to restore old Vault data; a fresh Vault creates new material |
| Databases, files and application content | Independent backups of their LXCs, VMs and volumes |
| GitHub-only credentials not yet archived | Original credential source; GitHub cannot export secret values |

The bootstrap record contains administrator credentials. The `external-secrets`
Vault policy explicitly denies its data and metadata paths; workload namespaces
must not be able to request it through an ExternalSecret.

`.env` restores only the values it contains. It does not currently contain application
JWT/signing keys, generated Grafana/RustFS passwords or all per-service Vault records.
For a faithful restore of those values, retain their backup/export; otherwise recover
external tokens from their issuer and deliberately regenerate app-owned credentials.
Changing signing/encryption keys can invalidate sessions or make existing data unusable.

If preserving the existing Vault, it uses file storage at `/opt/vault/data`, not Raft.
Take a consistent
backup with the Vault service or LXC stopped, including `/root/vault-init.json`,
configuration, TLS files and the unseal service/script. Terraform state does not
contain the Vault KV database or application data. Keep backups outside the Proxmox
disk being recovered and test restoring them in an isolated environment.

## Rebuild using the initial .env, without a Vault backup

1. Clone this repository and restore the protected `.env` to its root. If starting
   from the template, copy `.env.example` to `.env` and supply the initial values.
   Keep permissions at `0600`. Use repository-relative paths and run direct commands
   from the repository root:

   ```bash
   chmod 600 .env
   source .env
   ```

2. Confirm the existing R2 bucket and backend keys are intact. Review Proxmox node,
   network and storage settings for the replacement host. Do not discard existing
   state or blindly apply it to a different environment.
3. Restore/rebuild runner VM 101 locally using the Proxmox bootstrap. Registration
   uses `.env`'s `GITHUB_TOKEN`/`GITHUB_REPO`; no running Vault is needed. If a new
   Proxmox API token is issued, update `PROXMOX_PASSWORD` before Terraform runs.
4. Establish DNS and k3s, then provision/configure a fresh Vault using `.env`'s
   `VAULT_USERNAME`/`VAULT_PASSWORD`. Follow the dependency order and commands below.
   Preserve any surviving Vault data instead of reinitializing it.
5. Seed the fresh Vault and synchronize GitHub's Actions copies:

   ```bash
   just --justfile ansible/Justfile secrets-store
   just --justfile ansible/Justfile secrets-check
   just --justfile ansible/Justfile secrets-sync
   ```

6. Populate required application Vault records from their separate exports or issuer
   credentials before enabling dependent workloads. Only app-owned values explicitly
   generated by their roles can be recreated automatically. Restore application data
   separately, then reconcile Flux and verify workloads.

No `.env` is copied into GitHub or committed. Once Actions secrets are synchronized,
the existing workflows run using `${{ secrets.NAME }}`. Before that synchronization,
continue deploying locally from `.env` rather than relying on an empty Actions store.

## Restore an existing Vault from backup (optional alternative)

1. **Access Proxmox and locate backups.** Recover the existing node or restore its
   network/storage settings on the replacement. Preserve existing guests and IDs.
   Do not apply Terraform with empty state while the original resources still exist.
2. **Restore Vault LXC 201 first.** Restore its consistent backup, including its data
   and unseal material, to inventory address `192.168.1.3`. Start the existing Vault
   service; its installed unseal hook uses `/root/vault-init.json`. Do not initialize
   a fresh Vault over recovered data.
3. **Restore DNS and TLS reachability.** If AdGuard is unavailable, temporarily map
   `vault.internal.pavel-usanli.online` to `192.168.1.3` on the operator machine. Keep
   TLS verification enabled. Restore AdGuard from backup when needed.
4. **Authenticate to restored Vault.** Use protected recovery material available
   through Proxmox to obtain an administrative Vault session. The initial root token
   may have been revoked; if so, use the retained unseal material and Vault's root
   generation procedure. The restore helper needs `VAULT_ADDR` and `VAULT_TOKEN`,
   not a pre-existing `.env`, GitHub runner or remembered userpass password.
5. **Restore operator inputs.** Clone the repository and run:

   ```bash
   export VAULT_ADDR=https://vault.internal.pavel-usanli.online:8200
   # Supply VAULT_TOKEN through the protected recovery session.
   python3 ansible/bootstrap/secrets.py restore-env
   source .env
   ```

   The helper creates `.env` with permissions `0600` and refuses to overwrite it.
   Review an existing file before explicitly using `--replace-existing`.
6. **Reconnect R2 state.** Verify restored `R2_*` values point to the original bucket.
   Replace revoked credentials through Cloudflare account access. Keep the existing
   backend keys. Review plans when changing the Proxmox endpoint, node, storage or
   network; migration is not a blind replay of the previous deployment.
7. **Restore runner VM 101.** Prefer its backup. If rebuilding, run the local phases
   in [README.md](README.md). Registration uses the recovered `GITHUB_TOKEN` and
   `GITHUB_REPO`. Local recipes work before the GitHub runner is online.
8. **Repopulate GitHub secrets from Vault.** Check coverage before writing:

   ```bash
   just --justfile ansible/Justfile secrets-check
   just --justfile ansible/Justfile secrets-sync
   ```

   Sync checks every workflow input, then updates Actions secrets using the
   Vault-held `GH_ADMIN_TOKEN`. It does not delete other secrets. Retry after an
   interrupted update. GitHub variables such as `AWS_TERRAFORM_ROLE_ARN` are separate.
9. **Reconcile remaining infrastructure.** Restore service data before configuration.
   Run Terraform and matching Ansible workflows per resource. Verify k3s before
   re-running Vault's Kubernetes integration. Install Flux after Vault, NFS and
   required service secrets are ready.
10. **Verify and back up.** Confirm Vault reads, runner connectivity, R2 access,
    External Secrets synchronization and application data. Refresh independent
    backups and rotate recovery credentials when appropriate.

## First deployment with no Vault backup

External credentials must be supplied once because no existing Vault can provide
them. Prepare the ignored root `.env` using the root README and bootstrap README.

| Order | Action | Required inputs/dependencies |
|-------|--------|------------------------------|
| 1 | Create/reuse GitHub repository, Cloudflare tokens and R2 bucket | Provider account access; local `.env` |
| 2 | Bootstrap Proxmox, templates and runner VM 101 locally | Proxmox login, host password, GitHub PAT/repo; Cloudflare token for final TLS phase |
| 3 | Save generated Proxmox Terraform token in `.env`; populate initial Actions secrets | Local inputs; no Vault dependency |
| 4 | Provision/configure AdGuard or provide required DNS | R2, Proxmox, Cloudflare and AdGuard inputs |
| 5 | Provision/configure k3s, without Flux yet | R2, Proxmox and host/SSH credentials |
| 6 | Provision/configure Vault LXC, userpass, KV-v2 and Kubernetes auth | k3s running; Vault admin inputs, DNS and Cloudflare TLS credentials |
| 7 | Store operator inputs in Vault; seed or generate service records | Working Vault; local `.env` |
| 8 | Verify and synchronize GitHub credential copies | Vault-held GitHub admin PAT; all workflow inputs archived |
| 9 | Provision/configure NFS and remaining services, then install Flux | Working Vault, k3s, storage and service secrets |
| 10 | Verify applications and take recovery backups | Vault/application data and R2 state |

Core commands for stages 2–7:

```bash
just --justfile ansible/Justfile bootstrap-pw 192.168.1.50
# Save phase 1's Proxmox token in .env before running Terraform.
just --justfile terraform/Justfile deploy cloudflare zones/pavel-usanli.online/internal
just --justfile terraform/Justfile deploy proxmox adguard-lxc
just --justfile ansible/Justfile configure adguard-lxc
just --justfile terraform/Justfile deploy proxmox k3s-cluster
just --justfile ansible/Justfile configure k3s-cluster
just --justfile terraform/Justfile deploy proxmox vault-lxc
just --justfile ansible/Justfile configure vault-lxc
just --justfile ansible/Justfile secrets-store
just --justfile ansible/Justfile secrets-check
```

The full bootstrap includes a Cloudflare TLS phase. With only Proxmox login, early
phases can run locally, but the TLS phase and subsequent provisioning need external
credentials. Bootstrap `GITHUB_TOKEN` and `GITHUB_REPO` are local registration inputs;
`GITHUB_TOKEN` in Actions is GitHub's built-in token.

The current Vault playbook configures Kubernetes auth unconditionally, so k3s must
be ready before the full Vault playbook. The Flux playbook uninstalls/reinstalls Flux:
`configure k3s-cluster/flux` is an installation action, not a health check.

## Normal operation and rotation

`secrets-store` archives all inputs explicitly defined in `.env` into
`secret/homelab-infra-secrets` using kebab-case keys (`GH_ADMIN_TOKEN` becomes
`gh-admin-token`). It preserves additional Vault keys and refuses to replace differing
values without `--replace-existing`. Writes use KV-v2 CAS and read-back verification;
secret values are never printed.

Update a secret in Vault, restore the local copy when needed, then synchronize Actions.
The manual **Secrets - Sync from Vault** workflow uses the same helper on the self-hosted
runner with Python 3 and `gh`. It authenticates using existing `VAULT_USERNAME` and
`VAULT_PASSWORD` Actions secrets and an explicit Vault address. It needs no `.env`,
laptop session, cached Vault token or Vault CLI. Helper-created login tokens are
revoked afterward. Existing workflows continue using `${{ secrets.NAME }}`, keeping
runner/Vault recovery independent of a live Vault connection.

Before rotating the sync workflow's Vault password, keep a working local admin
session and perform the first sync locally; a revoked password cannot fetch its
replacement. Application-generated credentials remain in per-service Vault records.
Expired AWS SSO tokens are not recovery credentials; sign in again or restore the
separate GitHub OIDC role.

GitHub secrets cannot be downloaded. If `secrets-check` names an unarchived input,
recover its original value and add its kebab-case key to the bootstrap Vault record
before syncing. Do not replace a missing signing key with a newly generated one.
Some Terraform-managed credentials are retained in R2 state; the original Android
signing input was recovered from `homelab/github/jacred-tv-client.tfstate` and archived
in Vault. Inspect such state only through a protected process that does not print values.
